QMS · QA Manager

Система управления качеством тестирования

Единое рабочее место аналитика, тестировщика и администратора: требования, тест-кейсы, прогоны, трассировка и ИИ-ревью.

Проекты→ User Stories→ Тест-кейсы→ Тест-раны→ Покрытие

Зачем нужна система

Классические таблицы и разрозненные TestRail/Excel не закрывают связку «требование → кейс → результат».

Потеря трассировки

Не видно, какие user story закрыты тестами, а какие остались без покрытия.

Качество кейсов

Кейсы без шагов, предусловий и тегов копятся и не проходят ревью.

Разные роли

Аналитик проектирует покрытие, тестировщик исполняет, админ управляет доступом — нужны разные экраны.

Что это за продукт

Веб-приложение QA Manager (QMS) на Spring Boot: каталог тестов, требования и исполнение в одном контуре.

Для команды качества

  • Хранение проектов, секций, user story и тест-сьютов
  • Полноценные тест-кейсы: шаги, теги, приоритеты, статусы
  • Тест-раны с фиксацией Passed / Failed / Skipped
  • Матрица трассируемости «User Story × Test Case»

Отличие от «просто TMS»

  • ИИ-анализ соответствия кейсов требованиям
  • ИИ-ревью качества кейса с оценкой 1–10
  • Импорт секций и stories из Excel/CSV
  • Ролевой вход: Admin / Analyst / Tester

Три роли — три входа

После логина пользователь попадает на свой рабочий стол. Пароли хранятся в BCrypt.

ADMIN

/admin/users

Создание и редактирование пользователей, роли, активация и деактивация с причиной, статистика аккаунтов.

ANALYST

/projects

Проекты, секции, user stories, связь с кейсами, матрица покрытия, импорт требований.

TESTER

/project-qa

Тест-сьюты, кейсы, шаги, теги, комментарии, ИИ-ревью и выполнение тест-ранов.

Модель данных

Иерархия от проекта до шага — так, как думает QA-команда.

Project→ Section→ User Story
Project→ Test Suite→ Test Case→ Steps / Tags / Comments
Project→ Test Run→ Результат по каждому кейсу

Связь many-to-many: один тест-кейс покрывает несколько user story, одна story закрывается несколькими кейсами. Именно это питает матрицу трассируемости.

Тест-кейсы как центр системы

Не «название в списке», а полноценный артефакт тестирования.

4приоритета: Low → Critical
4статуса: Draft, Review, Active, Archive
Шагидействие + ожидаемый результат
Тегицветные метки в рамках проекта

Содержание кейса

Название, описание, предусловия, шаги, теги, связанные user stories и лента комментариев.

Операции

CRUD, поиск по сьюту, клонирование кейса вместе со структурой, добавление/удаление шагов и связей.

Требования и импорт

Аналитик ведёт секции проекта и user stories — вручную или пакетом из файла.

Excel / CSV

Поддержка .xlsx, .xls и .csv. Секции импортируются вместе с историями; отдельно можно загрузить список stories в секцию. Пакетная загрузка не «роняет» большой файл.

Связь с тестами

Любой кейс привязывается к user story. Связь двусторонняя: видно покрытие требования и «зачем написан» кейс.

Тест-раны — исполнение

Прогон собирается из отдельных кейсов или целых сьютов. Исполнитель и автор фиксируются.

Статусы рана

Не начат → В процессе → Завершён. Состав кейсов можно менять после создания.

Результат кейса

Не выполнен / Успешно / Провален / Пропущен + комментарий исполнителя.

Статистика

Счётчики и проценты passed / failed / skipped / not run по каждому прогону.

Фишка: ИИ-ревью тест-кейса

YandexGPT оценивает кейс по чеклисту качества и ставит общую оценку.

  • Атомарность — одна проверяемая функция
  • Теги: есть ли и насколько уместны
  • Полнота описания
  • Шаги с действиями и ожидаемым результатом
  • Адекватность предусловий
  • Связь с пользовательскими историями
8/10

Результат сохраняется в TestCaseReview и доступен повторно — не нужно гонять модель каждый раз.

Можно ревьюить один кейс или весь сьют разом.

Фишка: ИИ-анализ покрытия

Для всего тест-сьюта модель сопоставляет кейсы с user stories проекта.

Что делает

Строит промпт из списка stories и полных кейсов (описание, предусловия, шаги). Для каждого кейса пишет, каким требованиям он соответствует и почему — или что покрытия нет.

Куда кладёт ответ

Комментарии типа AI_GENERATED на кейсе. Рядом живут ручные комментарии команды. История анализа (промпт + ответ) сохраняется отдельно.

Комментарии и коллаборация

MANUAL

Обычные заметки тестировщика или аналитика с привязкой к пользователю.

AI_GENERATED

Автоматические выводы модели по соответствию требованиям.

SYSTEM

Служебные сообщения процесса — отдельный тип, не смешивается с людьми и ИИ.

Теги цветные и живут внутри проекта: smoke, regression, api, ui — без «глобальной свалки» меток.

Администрирование

Отдельный кабинет администратора, недоступный аналитику и тестировщику.

  • Создание пользователей: логин, ФИО, email, роль
  • Деактивация с причиной, повторная активация
  • Поиск по пользователям, REST API рядом с формами
  • Счётчики: всего / активных / администраторов

Безопасность

Spring Security, form-login, BCrypt, разграничение URL. Демо-учётные записи создаются при первом запуске: admin, analyst, tester.

Технологический стек

Backend

Java 17, Spring Boot 3.5, Spring MVC + Security, JPA/Hibernate, Validation

Данные

PostgreSQL, схема qms_projects, ddl-auto update

UI

Thymeleaf, Bootstrap 5, Font Awesome, кастомный градиентный интерфейс

ИИ и файлы

YandexGPT (IAM-токен с автообновлением), SheetJS на клиенте, Apache POI / CSV

Архитектура классическая layered: controller → service → repository → entity/DTO. Планировщик пересобирает матрицы и обновляет IAM-токен Yandex Cloud.

Карта возможностей

Уже умеет

  • Ролевой доступ и отдельные UI для аналитика и QA
  • Каталог кейсов со шагами, тегами, клонированием
  • Импорт требований из Excel/CSV
  • Тест-раны и живая статистика прогона
  • Матрица трассируемости
  • Два ИИ-сценария: качество кейса и покрытие stories

Для кого ценность

Аналитик — видит пробелы покрытия требований тестами.

Тестировщик — ведёт кейсы и отмечает результаты ранов.

Тимлид / QA lead — оценка качества кейсов и прозрачность прогонов.

Админ — контроль доступа без лезания в БД.
